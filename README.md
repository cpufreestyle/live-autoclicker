# 直播按钮自动点击器

对屏幕上**多个直播窗口**持续扫描，识别不定时弹出的「签到」「奖券」「领取」「兑换券 / 立即领券」等按钮，命中后自动点击一次。
识别采用**模板匹配 + OCR 双通道**：按钮样式固定时用截图模板最稳，按钮会变但文字不变时用 OCR 关键词。

> 合规提示：自动点击可能违反部分直播平台的服务条款，存在账号风控风险。请自行确认规则后再使用。

## 安装

需要 Python 3.10+（64 位）。

```bat
pip install -r requirements.txt
```

实测通过环境：Windows + Python 3.14 + numpy 2.4 / opencv 4.13 / mss 10.2 / rapidocr-onnxruntime 1.2.3（4K 屏、12 核）。
依赖按最低版本声明，不必严格对齐上面这套版本。

## 使用流程

```bat
python app.py
```

顶部是应用栏（程序名、当前状态「运行中 / 已停止」、三个窗口的实时统计、「▶ 启动」与全局热键提示），下面分四块：左上「监控窗口」、左下「按钮目标」、右侧「运行参数」（从右到左占满两行，滑杆右边实时显示当前值）、底部「运行日志」。

1. **添加监控窗口**：在「监控窗口」里点「新增窗口」→ 起个名字（如 `直播A`）→ 二选一定位方式：
   - **按窗口身份自动跟随**（推荐）：在「新增/编辑窗口」对话框里点「自动识别窗口身份…」，5 秒倒计时内把鼠标挪到直播窗口画面上停好别动，类名/进程名/标题就自动填好了（识别结果会告诉你这组身份当前命中几个窗口；命令行等价物是 `python selftest.py --pick --write`），或 `python selftest.py --windows` 看全部窗口的标题、类名和进程，然后在「窗口标题包含 / 窗口类名包含 / 进程名包含」里填能唯一命中直播窗口的那几项。标题是房间号旃1场一变，这时把标题留空、只填类名 + 进程名就行。程序每轮扫描实时取该窗口矩形，直播窗口**挪位置、改大小、换直播间都不用重新框选**；同身份多窗口（微信主界面 + 直播小窗 / 多开房间）会粘性续跟上次那个、不来回跳，且每次点击前会按窗口最新位置校正偏移——OCR 那一两秒里就算窗口被拖动也点得中；画面近乎不变时（流卡住/等待开播/弹窗已挂起但在冷却）会自动跳过这一轮的 OCR+模板省算力，画面一变立刻恢复，绝不漏点；再配「底部裁切(像素)」把窗口下方的弹幕带切掉。 改 `config/*.yaml`（`--pick --write` 或手改）后运行中的程序约 0.2 秒自动套用，无需重启。
   - **框选区域**：「框选区域」在直播画面上拖一个矩形，只框住视频区域比全屏快得多；位置一变就要重框。
   - 两项都留空 = 按整屏扫描（多窗口时不建议）。有几个直播就加几个窗口，也可以「编辑」里单独给某个窗口设更长的扫描间隔。
2. **添加按钮目标**：在「按钮目标」里点「新增」→
   - 填名称，如 `签到`
   - 点「框选截图…」把按钮本体截成模板（**推荐**，最可靠；等按钮出现时再截）
   - 和/或填 OCR 关键词，如 `签到, 立即签到`
   - 设冷却时间（同一窗口的同一按钮只点一次，默认 30s）
   - 「生效窗口」留空 = 所有窗口都找；填 `直播A` 或 `直播A, 直播B` = 只在这些窗口里找
3. **测试扫描一次**：对每个启用的窗口各截一帧跑检测但**不点击**，日志显示命中了哪个窗口的哪个目标、置信度、准备点在哪里。用它来调阈值和关键词。
4. **启动**：默认**打开软件就会自动开始运行**（等 3 秒，日志会提示）。不想自动跑就在「运行参数」里取消勾选「打开软件后自动开始运行」，改回手动点「▶ 启动」或按 `F1`。运行中再按 `F1` 全部停止。
   运行中每个窗口一行独立统计（扫描次数 / 点击次数 / 状态），改配置不用停：新增窗口会立刻起一条扫描线程，删除或停用的窗口只结束它自己那一条。
5. 想让某个按钮在各窗口有不同的偏移或冷却，选中目标点「复制到所有窗口」，会按窗口各生成一份并**自动停用原目标**（原目标默认对所有窗口生效，留着会和副本重复点同一个按钮）。

误点时可用 pyautogui 的保险丝：把鼠标**猛甩到屏幕左上角**会中断移动。

不开 GUI 调参，适合先看清屏幕上有哪些文字、该填什么关键词：

```bat
python selftest.py --list                                  "列出窗口与适用目标，不截图"

python selftest.py --pick                                  "鼠标移到直播窗口上停好别动，倒计时结束自动锁定，读出它的类名/进程/标题，给出现成配置（只读）"
python selftest.py --pick --write                          "在上一项基础上，直接把这组身份写回 monitors.yaml 的「直播间」条目"
python selftest.py --ocr-only                              "打印识别到的全部文字与坐标"
python selftest.py --ocr-only --window 直播A                "只看某个窗口区域"
python selftest.py --image shot.png                        "用一张截图离线测检测逻辑"
python selftest.py --ocr-bench                            "扫几档 ocr_max_side，报耗时/文字召回"
python selftest.py --ocr-bench --ocr-provider directml  "换 GPU 后端再扫一遍，和 CPU 比速度"
```

## 运行日志

程序把所有扫描日志写到 **`logs/run.log`**（源码跑写在仓库根目录，打包后写在 exe 同级目录），界面上点「打开运行日志」直接跳到那个文件夹。

界面里的日志框只留最近 400 行，文件里是全量：每次命中/点击、每轮 OCR 认到多少文本框、关键词没匹配上时**最相似的那串原文**、窗口丢失与找回、单帧耗时超预算，都会带时间戳落盘。排障时先看这个文件，比截图猜快得多。日志由独立线程批量写，队列满就丢一条，磁盘出问题也不会拖慢或中断扫描。

典型用法：

```bat
type logs\run.log | findstr 命中        REM 看有没有点中过
type logs\run.log | findstr OCR          REM 看 OCR 到底跑没跑、认到多少字
type logs\run.log | findstr 最像         REM 看关键词和实际文字的差距
```

`selftest.py` 自检的 OCR/命中结果也写进同一个文件，方便和真实运行的记录对照。

## 配置

`config/settings.yaml`（全局参数，界面里也能调）

| 键 | 说明 |
| --- | --- |
| `scan_interval_sec` | 全局扫描间隔。按钮弹出越快值越小（越小越吃 CPU） |
| `jitter_sec` | 间隔随机抖动，模拟人工节奏 |
| `match_threshold` | 模板匹配阈值，常用 `0.80~0.90` |
| `ocr_min_score` | OCR 置信度下限，低于此值的文字忽略 |
| `ocr_max_side` | OCR 前把帧最长边**压到**该值。**4K/高分屏必须保留**，否则 onnxruntime 报 `bad allocation`。调大会更准：真机微信直播窗（1836x1069）实测 1600 只剩 85% 文字召回、1920 100%，耗时只差 2%；想彻底不缩放就填 `4096`（≥ 窗口宽度即不降采样） |
| `ocr_min_side` | 小窗口最长边不足该值时先**放大**到它再识别。设 0 时小区域会整段漏检文字（同一张 600x260 截图实测：0 漏检、736 及以上正常），且放大几乎不额外耗时 |
| `ocr_concurrency` | 同时跑 OCR 的窗口数。共享一份模型，用信号量限流；默认 1，窗口多又卡时保持 1 |
| `ocr_threads` | **一次 OCR 能用几个线程**，默认 3。不限的话 onnxruntime 会按 CPU 核数开满，实测一帧吃掉 4~6 个核、连续扫描会把整台电脑拖到没反应；而且这几个 PP-OCR 模型太小，线程开多了反而更慢（12 核机实测：3 线程 2.0s/帧、12 线程 5.7s/帧）。卡就往下调，1 最省 |
| `ocr_provider` | OCR 推理后端：`auto`（默认，装了 `onnxruntime-directml` 就走显卡，没装照旧跑 CPU，行为完全不变）/ `cpu` / `directml`（强制显卡，起不来自动退回 CPU）。真机实测同一档位 **1501ms → 819ms**，文字召回一致。用显卡：`pip install onnxruntime-directml`，卸载即回退 |
| `ocr_scan_every` | 隔几轮跑一次 OCR，默认 1（每轮都跑）。模板匹配仍然每轮跑，只有最贵的 OCR 降频。620x300 带弹幕的窗口实测设 2 省 42% CPU；代价是最坏多等一个扫描间隔，因为按钮会一直显示到被点掉，所以不会漏点 |
| `ocr_idle_every` | 空闲自动降频：连续这么多轮什么都没扫到时，OCR 改成每这么多轮才跑一次，一有命中立刻恢复每轮跑（默认 2）。直播间绝大多数时间没有弹窗，这段 OCR 是白烧 CPU——816x1000 真实直播画面实测一帧 0.55~2.68s（平均 1.59s），按 1.5s 间隔连扫 10 分钟，默认档比每轮跑**省一半 OCR**、设 3 省 67%。真机连着扫 601 帧实测 OCR 282 次 = **47%**（命中/点击会重置空闲计数并把比值拉高一点），假直播窗 E2E 为 51%。代价是弹窗最坏晚一个扫描间隔被点到：会一直挂到被点掉的弹窗没损失，但自己几秒就消失的弹窗（红包倒计时之类）可能整轮错过，那种场景填 1。设 1 就是改之前的行为 |
| `click_guard_sec` | 同弹窗防重复：点过一发后，附近多少秒内不再点第二下（默认 2.5s，填 0 关闭）。一张弹窗里往往同时写着「立即领券」和「奖券」，两个目标各有一份冷却、互不阻塞，真机日志里每张弹窗被连点两下（19:42:57 兑换券 (1503,678) → 19:42:59 奖券 (1481,543)，相距仅 135px）。开启后这第二下会被拦下并记进日志，冷却照常计时，之后弹窗还在照样补点 |
| `use_pydirectinput` | 直播客户端收不到模拟点击时打开 |
| `raise_before_click` | 命中按钮但那个点被别的窗口盖着时，把监控窗口**临时顶到最前面**再点，点完立刻还原层次（默认 `true`）。后台抓窗只负责「看得见」，点击永远只发给最顶层的窗口——不切换就一直停在「看得见点不中」。设 `false` 则维持老行为：被挡住就跳过并在日志里说明。抢焦点只发生在「这一发马上要点了却被挡住」时，且同一窗口最多 4s 抢一次 |
| `bring_window_on_screen` | 直播窗口整个或部分停在可见屏幕外时（显示器被拔掉、远程桌面改过尺寸，窗口还留在老坐标上），先把窗口**最小平移进屏幕**再点，点完立刻还原位置（默认 `true`）。否则落在屏幕外的命中一律跳过并在日志里说明——那些坐标会被 Windows 夹到屏幕边缘，点中的其实是边缘上无关的窗口 |
| `humanize_click` | 点击前平滑移动 + 随机延迟 |
| `hotkey_toggle` | 启停热键 |
| `auto_start` | 打开软件后自动开始运行（默认开）。取消勾选后必须手动点「▶ 启动」或按 `F1` |
| `scales` | 模板多尺度缩放系数，画面分辨率会变时加几档 |

`config/monitors.yaml`（监控窗口清单，一个条目 = 一条扫描线程）

```yaml
monitors:
  - name: 直播A                 # 目标靠这个名字绑定，不要重复
    window_title: ''            # 身份一：标题子串。直播窗口的标题常是房间号，换房间就失效
    window_class: ''            # 身份二：Win32 窗口类名，如 Chrome_WidgetWin_1
    window_process: ''          # 身份三：进程 exe 名，如 Weixin.exe
    crop_bottom: 220            # 跟随时从窗口底部裁掉的像素，用来切掉弹幕带；0 = 不裁
    crop_right: 0               # 右侧裁切：切掉右侧一列（浏览器直播间的聊天栏），里面的群名/弹幕
                              # 也常出现「签到/领券」，不裁就会整列判成命中点过去；0 = 不裁
    crop_left: 0                # 左侧同理（微信左侧是会话列表）。裁切按窗口边缘的固定像素算，
                              # 窗口改大小就偏，所以只在布局固定时填。微信视频号直播间的弹窗盖在
                              # 侧栏上，两侧都别裁，会把「立即领券」自己裁没
    background_capture: false  # 实验性：被无关窗口盖住、或整屏抓到黑帧时，才用 PrintWindow
                                 # 后台抓窗口自己的像素（不抢焦点、被遮住也能抓）。默认先走整屏
                                 # mss：兑换券弹窗是独立顶层窗口，PrintWindow 拍不到它
    region: [200, 440, 600, 260]   # 三项身份都留空时用固定区域；null = 整屏
    enabled: true
    scan_interval_sec: null     # 留空用全局值
    ocr_max_side: null          # 留空用全局值
```

身份三项（`window_title` / `window_class` / `window_process`）填几项就要求**同时满足几项**，都留空才会退到 `region`。直播窗口的标题常是房间号、换个直播间就对不上，所以现在可以**只填类名 / 进程名而不填标题**。这三个值用 `python selftest.py --windows` 把当前所有窗口的“类名 / 进程 / 标题”列出来挑，挑能唯一命中直播窗口的组合。命中多个时取面积最大的那个；
找不到窗口时该窗口**暂停扫描**并在日志里提醒一次，窗口回来就自动继续——不会退回整屏去点桌面。

`config/targets.yaml`（按钮目标）

```yaml
targets:
  - name: 签到
    template: templates/签到.png      # 可为空
    ocr_keywords: [签到, 立即签到]     # 可与模板并存
    click_offset: [0, 0]              # 按钮中心偏移
    cooldown_sec: 30
    enabled: true
    match_threshold: null             # 留空用全局阈值
    monitors: []                      # 空 = 所有窗口；否则填窗口名，如 [直播A, 直播B]
```

兑换券 / 奶券弹窗里要点的按钮叫「立即领券」，弹窗里其余文字（兑换券、9.24 奶券、指定商品可用）都不该点，
所以关键词只能指向按钮文字本身，否则会把整段文字的中心当成按钮点：

```yaml
  - name: 兑换券
    template: ''
    ocr_keywords: [立即领券, 立即领取, 领券, 立即领]
    cooldown_sec: 30                  # 同一张券点过就不再点；新券弹出来还会点
```

`config/targets.yaml` 里已经预置了这一条，开箱就能点「立即领券」。想让识别更稳，可以在按钮弹出时用界面里的
「框选截图…」把按钮本体截成模板填到 `template`。注意界面保存时会重写 `targets.yaml`，手写的注释会丢，说明写在 README 里。

## 工作原理

```
app.py (tkinter 主线程：界面、日志、高亮、热键)
  └─ Engine
       ├─ MonitorWorker「直播A」线程 ─┐
       ├─ MonitorWorker「直播B」线程 ─┼─ 各自：解析区域 → grab → Detector.scan → 点击，各自 interval±jitter
       └─ MonitorWorker「直播C」线程 ─┘
            共享：OcrEngine（模型只加载一次 + ocr_concurrency 信号量限流）
                 CooldownTracker（按「窗口|按钮」记键）
                 Clicker（全局鼠标锁，串行点击）
            回传：事件队列 → 主线程写日志 / 高亮框 / 刷新该窗口那一行统计
```

- **不定时**问题由「持续扫描 + 抖动间隔 + 每窗口每目标冷却」组合解决：按钮任意时刻弹出都会在下一个周期被发现，且只点一次。
- **多窗口**是每窗口一条线程，互不阻塞；某个窗口卡住只拖慢它自己那一行。OCR 是主要开销，所以用信号量限并发而不是无限并行（并发过高会互相抢核，反而更慢）。
- 一帧只做**一次** OCR，再按关键词分别匹配各目标，所以同一帧里多个关键词目标共享识别结果。
- **按标题跟随**的窗口每轮先用 Win32（`EnumWindows` + DWM 扩展边框，去掉那圈透明的拖拽边）现取实时矩形，再按 `crop_bottom` / `crop_right` / `crop_left` 把弹幕带和侧边聊天列裁掉（三侧都是按窗口边缘的固定像素算，窗口一改大小就偏，微信视频号那种弹窗盖在侧栏上的布局除外）；截图、检测、坐标换算用的是同一份矩形，所以窗口移动后点击位置依然对得上。填身份时以 `selftest.py --windows` 的实际输出为准：微信 4.x 的直播间是 `WeChatAppEx.exe` + `Chrome_WidgetWin_0`，配成 `Weixin.exe` 会一直找不到窗口、整轮停扫。
- **弹窗也算「够得到」**：直播间的「兑换券 / 红包」弹窗是盖在直播窗上的**独立顶层窗口**，
  不是直播窗的子窗口。所以命中之后程序问 Windows「这个点现在归谁」时，除了直播窗自己，还认
  「几乎整个嵌在直播窗矩形里的独立顶层窗口」——弹窗整块落在直播窗里就算数，这一发照点。
  完全无关的窗口（比如另一块屏幕上的浏览器）和只搭个边的仍然拦下，照旧先提窗再点。
- **CPU 是有预算的**：OCR 建推理会话前会把 onnxruntime 的 intra-op 线程与 OpenCV 一起限到 `ocr_threads`（库本身没有传这个参数的入口，所以是替换掉 rapidocr 模块里的 `SessionOptions` 名字）；每帧之后还强制留出「间隔 × 30%」的空闲，单帧比间隔慢时也不会变成 100% 占空比。这两条合起来才让桌面在你挂着扫的时候依然能操作。
- **冷却中的按钮不值得再扫**：点过一次之后目标进入 `cooldown_sec`，这期间就算 OCR 出同一个按钮也不会点。所以现在检测器先把冷却中的目标挑掉，只剩冷却目标时整帧（截图 + OCR）直接跳过，日志说一句「全部按钮冷却中」就安静等着，到点自动恢复。620x300 带弹幕的窗口实测：15 秒内 OCR 从 10 帧降到 1 帧，平均占用从 2.03 核降到 0.34 核。
- **OCR 的耗时几乎只取决于「画面里有多少行字」**：同一块 620x300 区域，滚动弹幕时约 1.0~1.2s/帧，弹幕停下、画面干净时 0.4s/帧，整屏则能到十几秒。所以省 CPU 的第一杠杆永远是 `crop_bottom` 裁掉弹幕带、以及只框住视频画面，而不是调线程数。
- **截图默认整屏，后台抓窗只在被盖住时兜底**：按身份跟随的窗口每轮先整屏 mss 截一次，
  只有「窗口被无关窗口整个盖住」或「整屏抓到黑帧（窗口整个在屏幕外）」时，才改用 Win32 `PrintWindow`
  + DIB section 读窗口自己的像素（被别的窗口盖住也能抓，不抢焦点）。为什么默认整屏：直播间的
  「兑换券 / 红包」弹窗多是盖在直播窗上的**独立顶层窗口**，`PrintWindow` 只拍得到直播窗自己，会把
  弹窗整块漏掉。2026-09-26 真机连扫 68 帧一帧都没拍到过弹窗、用户连报「检测不到」，根因就在这。
  后台抓到的帧若矩形和本轮对不上（窗口刚好在两次调用之间动了），宁可回退整屏白扫一次也不点歪；
  抓取失败或拍到近乎纯色的帧（GPU/DirectX 渲染的视频常这样）时同样回退整屏。
  `background_capture: false` 时完全不碰 `PrintWindow`。
- **每 40 帧往日志里报一次体检**：「已扫 N 帧，命中 X，点击 Y，OCR n 次/m 个文本框，
  冷却中跳过 a 帧，画面没变跳过 b 帧」。关键词一个都没匹配上时，还会把 OCR 实际读到的文字列出来
  （或给出和最像的一段文字的相似度），并提示下一步该怎么办。「点了启动却什么都没发生」时，
  看这一行就能分清是 OCR 根本没读到按钮、读到的字和关键词对不上、还是整帧都在被跳过，不用猜。
- 方向分类（`use_angle_cls`）在建会话时就关掉了：直播浮层的中文按钮永远是正着写的，而这个分类器是**每检出一个文字框**多跑一次推理，弹幕密的时候纯属白给。关掉后分类器的模型会话根本不创建。

## 常见问题

- **点「启动」后整台电脑卡住、像死机**：根因是 OCR 的线程数。onnxruntime 默认按 CPU 核数把 intra-op 线程开满，而 PP-OCR 那几个模型太小、线程多了纯属内耗——12 核机实测一帧平均吃掉 4~6 个核还要 5.7s；再叠上「单帧比扫描间隔还慢时，下一帧零空闲立刻开始」，占空比就是 100%，桌面再也抢不到 CPU。现在默认把 OCR 与 OpenCV 限到 `ocr_threads: 3`（同一帧实测 2.0s / 3.2 核），并且每帧之后至少让出「间隔 × 30%」的空闲。仍然卡就依次：把 `ocr_threads` 降到 1~2、`ocr_concurrency` 保持 1、区域只框住视频画面（别用整屏）、加大 `scan_interval_sec`。
- **日志说「全部按钮冷却中，约 Ns 后再扫」**：这是正常省电行为，不是卡住。上一个按钮刚点掉、还在 `cooldown_sec` 里，这期间扫到也不会点，所以整帧截图和 OCR 都跳过，到点自动恢复。统计表里的扫描次数在这期间不涨，就表示「确实没白跑」。想一直盯着就把 `cooldown_sec` 调小。
- **挂着扫还是很吃 CPU**：按收益从大到小依次处理。① 先确认只框住了视频画面（整屏是几十倍开销），并按 `selftest.py --ocr-only` 量到的弹幕 y 坐标填 `crop_bottom` 把弹幕带裁掉——OCR 的时间几乎全花在「画面里有多少行字」上；② 确认 `ocr_idle_every` 没被设成 1（默认 2，没弹窗时自动只跑一半 OCR），再把 `ocr_scan_every` 设 2；③ `ocr_threads` 降到 1~2、`ocr_concurrency` 保持 1；④ 加大 `scan_interval_sec`；⑤ 给按钮截模板、把关键词留空——纯模板目标一帧只要几毫秒。
- **同一张弹窗被点了两次**：弹窗里常常同时写着「立即领券」和「奖券」两个目标词，两边的 `cooldown_sec` 各算各的，于是一张弹窗先点主按钮、零点几秒后又点一下旁边的文字。默认的 `click_guard_sec: 2.5` 会把这种「刚点过附近又命中」的第二下拦掉（日志写「同一张弹窗」，统计行也有「同弹窗重复点击拦下 N 次」）；填 0 就恢复每见每点。远处新弹出来的按钮不受影响。
- **窗口缩放后点不准**：程序已开启进程级 DPI 感知，但**改过 Windows 缩放比例后要重启程序**再重新框选区域。
- **小窗口里的按钮识别不到**：文字太小会被检测网络整段漏掉。把 `ocr_min_side` 调大（960 → 1280），或让框选区域更大一些。
- **OCR 太慢（一帧要一秒多）**：想再快一倍就先把显卡用上——`pip install onnxruntime-directml`，`ocr_provider: auto`（默认就是），真机 1836x1069 直播窗实测 1501ms→819ms，识别结果一致；卸载该包即回到 CPU。再往下调就是拿精度换速度：
  `python selftest.py --ocr-bench` 会对当前窗口扫几档 `ocr_max_side`（当窗口比 1920 宽时另加一档「原尺寸」），打印每档耗时、文本框数、文字召回，并给出建议。实测（1624x1000 真实窗口）：960 与 1600/1920 召回一致（都是 100%），但比 1920 快 18~23%；640 开始掉字（召回 92%）。**注意微信直播窗（1836x1069）例外：1600 只剩 85% 召回，得用 1920。**换窗口、换分辨率后重扫一遍再定。
- **按钮明明在那儿却读不到 / 召回不全**：`ocr_max_side` 压太狠了。真机实测同一个直播窗，1600 只剩 85% 文字召回、1920 才有 100%——小字按钮正好是被丢掉的那一批。先用 `--ocr-bench` 看各档召回，再把这个值调到召回满的那一档（≥ 窗口宽度即可不缩放）。
- **OCR 报 `bad allocation`**：整屏帧太大导致推理内存分配失败。确认 `ocr_max_side` 生效（默认 1920），必要时调到 1280。
- **日志提示「单帧耗时超过设定间隔」/ 扫描很慢**：OCR 耗时由「区域大小 + 区域内文字块数」共同决定，差别极大。先量自己机器的真实值：`python selftest.py --ocr-only --window 窗口名`。参考：600x260 的小直播窗口（3~5 处文字）约 0.5~0.8s；整屏 3840x2160 在文字较多的桌面（72 处文字）实测 12~23s。所以**务必只框住直播画面，别用整屏**；仍不够快就依次加大 `scan_interval_sec`、把 `ocr_min_side` 设为 0、把 `ocr_concurrency` 调到 1、或改成只用模板匹配（不填关键词的目标几乎不耗时）。
- **日志提示「命中点落在本程序自己的窗口里，已忽略」**：整屏扫描时 OCR 会读到本程序界面上的「签到」「奖券」列表项和日志文字，点下去等于点自己，还会把新日志再读成命中形成自激。程序按屏幕坐标询问 Windows「这个点最顶层是谁」，是自己的窗口就丢弃该命中（只报一次）。**盖在本程序上面的直播窗口不受影响**，照常点击；根治办法仍是给监控窗口框选直播画面区域。
- **按下「停止」后界面有几秒像卡住**：改好了。停止本来要等扫描线程把当前那一帧做完（单帧最长 3~5s，卡在长帧 OCR 上），在 tkinter 主线程里同步等，界面就「未响应」几秒。现在界面点「停止」只劝停、立刻回到停止态，等线程退干净这件事放到后台线程做；再点「启动」时也会先把上一轮的线程等掉，不会出现同一窗口两条扫描线程同时扫。
- **直播间忽然被关掉还点了下去**：从截图到点击隔着几次 OCR（可能一两秒），这期间窗口可能被关。窗口一没，截图时记下的矩形只是屏幕上一段旧坐标，点中的会是桌面或者正好飘到那儿的别的窗口。现在点击前会确认窗口还活着，窗口已消失就安静跳过这一发，日志只提醒一次（「点击前发现直播窗口已消失」），窗口回来后自动继续；命中次数照常统计。
- **日志说「点击点落在屏幕可见范围外」**：直播窗口停在屏幕外了。常见原因是显示器被拔掉 / 切换、或用 ToDesk、VNC 等远程桌面之后桌面尺寸改了，窗口还留在旧坐标上。默认（`bring_window_on_screen: true`）会自动把窗口挪进屏幕再点、点完还原位置，日志里会够写明「原位置 x,y 不在当前桌面内」；不想移动窗口就把它改 `false`，此时落在屏幕外的命中会被安全跳过。
- **命中了却点不到 / 日志说「被别的窗口盖着，已跳过」**：后台抓窗（`background_capture: true`）能拍到被遮住、甚至最小化的窗口，但点击永远只发给最顶层那个窗口。所以命中之后程序会再问一次 Windows「这个点现在归谁」，不是目标窗口就跳过并只提醒一次。
  - 默认行为（`raise_before_click: true`）：确认被挡住的那一刻，把监控窗口**临时顶到最前面**再点，点完立刻还原层次；日志会写「已把直播窗口切到前台后再点」。
    这里借的是 `SetWindowPos(HWND_TOPMOST)`——只调 `BringWindowToTop` / `SetWindowPos(HWND_TOP)` 时，Windows 经常把窗口留在原处，尤其压不住正在前台那个程序的界面（本程序自己的窗口就是最常见的那块），实测必须借 topmost 才顶得动。
  - `raise_before_click: false`：回到老行为，只在日志里说明，不动任何窗口。
  - 弹窗被盖住但日志里既没有「切到前台」也没有「盖着」：看是不是目标按钮正在 `cooldown_sec` 冷却里。
  - 最常见的「别的窗口」就是本程序自己的界面——它盖在直播窗上时一样会触发拦截，所以直播窗最好只占屏幕一块，别被主界面压住。
  - **弹窗不算「别的窗口」**：整块嵌在直播窗里的兑换券弹窗，归属判断会算「够得到」，命中后照点，
    不会跳「被别的窗口盖着，已跳过」。
- **点到了弹幕里的字**：直播窗口的弹幕/评论里也常出现「签到」「红包」「领取」，整窗框选时 OCR 会把它们当成按钮。跟随时把弹幕带裁掉：`crop_bottom` 管下方，`crop_right` 管右侧一列（浏览器直播间的聊天栏），`crop_left` 管左侧一列（微信左侧的会话列表），或改成固定区域只框视频画面；再不行就改用按钮模板匹配，或把关键词写得更长更具体（如「立即签到」而不是「签到」）。另外：同一个目标的关键词在同一帧里同时命中时（弹幕里的「先领券」和真按钮「立即领券」），只点关键词更完整的那些框——长关键词优先，短关键词找到的弹幕不会把真按钮抢走。
  **微信视频号例外，别用裁切**：实测它的兑换券弹窗落在窗口 x 1230~1654，右边聊天列从 x≈1560 开始，两者重叠——一裁就把「立即领券」自己裁没了。微信这种「弹窗盖在侧栏上」的布局只能整窗跟，把关键词写长、或给弹窗截模板。
- **直播窗口必须前台才能抓到 / 一抓屏就把直播切到前台**：默认整屏截图就看得见，而且不抢焦点、
  不会把直播窗切到前台；只有直播窗自己被无关窗口整个盖住时，才需要给该窗口开启
  `background_capture: true`（“监控窗口”对话框里的“后台抓窗口(PrintWindow)”勾选），它直接向窗口要像素。
  三点要注意：只在按身份跟随（填了标题/类名/进程名）时才能用；`PrintWindow` 只拍直播窗自己，
  **盖在直播窗上的兑换券弹窗是独立顶层窗口，拍不到**——要抓弹窗就保持整屏截图（直播窗自己可见即可）；
  部分 GPU 渲染的视频 `PrintWindow` 只能抓到黑屏，这时程序会自动回退整屏截图（日志里看不到报错）。
- **直播窗口会挪位置、改大小，框选的区域一会儿就不对了**：改用「按窗口标题自动跟随」——`window_title` 填一段稳定的标题子串（`python selftest.py --windows` 看当前标题），程序每轮现取矩形。注意别填整条标题：直播间名称常在标题里变，留「直播」「视频号」这类稳定片段。
- **日志说「找不到标题含…的可见窗口」**：直播窗口被关掉或最小化了（最小化的窗口在屏幕外，截到的是黑帧，所以不算命中）。该窗口会暂停扫描、只提醒一次，把窗口恢复显示就自动继续。微信 4.x 特别注意：视频号直播间的窗口进程是 `WeChatAppEx.exe`（类名 `Chrome_WidgetWin_0`），不是 `Weixin.exe`——后者的主窗口常年被挪到屏幕外（负坐标），程序只会当它不存在。填身份前先 `python selftest.py --windows` 核对直播间那一行的进程与类名，照着填「进程名包含」和「窗口类名包含」。
- **两个挨着的按钮点到同一个位置**：OCR 会把紧挨着的文字读成一个框（如「签到奖券」）。程序按关键词在框内的字符占比切分点击点，一般能分开；若仍不准，给其中一个目标设 `click_offset`，或把两个按钮分别截成模板用模板匹配。
- **OCR 没反应**：仅填关键词的目标需要 `rapidocr-onnxruntime`；启动时会打日志「正在加载 OCR 模型…」，首次约 1~2s。
- **识别不到 / 误识别**：重新截更干净的模板（只截按钮、避开动图背景），或把 `match_threshold` 从 0.9 逐步降到 0.8；文字类按钮优先用 OCR。
- **点击无效**：勾选 `use_pydirectinput`（部分客户端只认硬件输入事件）。
- **改了 `ocr_concurrency` 没生效**：并发数在启动时建信号量，运行中改会提示「需停止后再启动才生效」。
- **日志说「模板文件不存在或无法访问」**：模板 PNG 被移动或删掉了。该目标只会提醒一次（不每帧刷屏），重新截图或改回路径即可；这期间只有 OCR 通道在工作。
- **手改 yaml 改坏了**：程序启动时会自动校正并逐条写进日志（如「区域应为四项，已改为按整屏扫描」「这些键不认识（可能拼错）」）。YAML 语法本身错了没法猜你的意图，会直接弹窗说明是哪个文件、哪一行。
- **换了显示器/分辨率后一直报扫描异常**：区域坐标已经落在屏幕外了。启动时的检查会在日志里点出是哪个窗口，重新「重新框选」即可（按标题跟随的窗口不受影响，每轮都是实时矩形）。
- **一条都没命中，但界面上没有任何报错**：打开 `logs\run.log` 看两行就够——
  - 日志里**完全没有 `OCR N 次/M 个文本框`**：OCR 通道没起来。打包版最常见原因是 PyInstaller 把 `C:\Windows\System32\HWAudioDriverLibs` 里那份互不兼容的 `msvcp140.dll` 平铺进了 `_internal`，它遮蔽了正确版本，`onnxruntime.dll` 的 DllMain 直接以错误 1114 失败，整条 OCR 静默失效。新版 `build.bat` 已在打包时删掉这两个文件；自己打的话删掉 `dist\LiveAutoClicker\_internal\msvcp140.dll` 和 `MSVCP140_1.dll` 即可（正确的 CRT 在 System32 里）。
  - 日志里有 `OCR N 次` 但 0 命中：看它打印的「最像 xxx(相似度 0.50)」，那就是 OCR 真实读到的文字，把关键词改成那个样子，或改用按钮模板匹配。
- **命中/点击的按钮不是想要的**：`logs\run.log` 里每条命中都带 `(来源, 置信度) → 绝对坐标`，照着坐标去屏幕上比一下，就知道点到的是弹幕里的同类词还是侧栏里的群名。
- **CPU 偏高**：增大 `scan_interval_sec`、把 `ocr_scan_every` 设为 2~3（隔轮才跑 OCR）、确认 `ocr_idle_every` 没被设成 1、缩小各窗口区域并裁掉弹幕带、停用不用的窗口，或删掉不用的模板目标。
- **YAML 注释丢了**：界面里改参数会重写 `config/*.yaml`，注释与排版不保留，值仍是有效的。手工编辑前先退出程序。

## 图标与主题

- **换图标**：把方形源图覆盖 `assets/app_icon_source.png`，跑 `python assets/make_icon.py`，它会一次生成 `app_icon.ico`（标题栏/任务栏用，含 16~256 七个尺寸）和 `app_icon.png`（界面左上角品牌区用——Tk 的 `PhotoImage` 读不了 ico，所以必须同时有 png）。改完记得重跑 `build.bat`，ico 才会打进 exe 图标里。
- 圆角由脚本统一裁（半径取边长 22 %），源图画成满幅方图就行；脚本会先把图放大 110 % 再居中裁回，把源图自带的外发光推到画布外，否则每个尺寸四周会留一圈黑边。
- **配色与控件样式全在 `ui/theme.py`**，界面代码只引用样式名（`Primary.TButton`、`Card.TLabelframe`、`Hint.TLabel`…），改主题不用翻界面文件。这里用的是 `clam` 主题：Windows 自带的 `vista` 会直接忽略大部分配色选项，写了也不生效。
- 复选框走内置的 `Toolbutton` 样式（整条文字即开关，选中时文字变蓝底），而不是默认勾选框：`clam` 的勾选指示器是张固定的「方框里画叉」位图，高 DPI 下把框放大叉也跟着放大，看着更像「取消」。
- 4K/225% 下所有间距、控件尺寸都经过主窗口的 `_px()` 换算；字号用「点」写，Tk 会随系统缩放自动放大，不需要再乘。

## 打包 exe

```bat
pip install pyinstaller
build.bat
```

产物是 `dist\LiveAutoClicker\LiveAutoClicker.exe`，整目录约 190MB（OpenCV + OCR 模型），分发时要**整个目录一起拷**，不能只拿 exe。

- **配置在 exe 同级**：打包后程序把「exe 所在目录」当根目录，`config\` 与 `templates\` 会被复制到 exe 旁边，改这两处即可；`_internal\` 里没有配置，也不用管。`build.bat` 用 `xcopy /D` 复制，不会覆盖你已经在 dist 里改好的配置。
- **`assets\` 同样在 exe 同级**：界面品牌区读的是 `assets\app_icon.png`，找不到就只是不显示小图标，不影响功能。`--icon assets\app_icon.ico` 只决定 exe 文件本身的图标；`build.bat` 开头会检查 ico 在不在，缺了直接报错提示先跑 `assets\make_icon.py`，免得打到一半才失败。
- **DPI 由 `app.manifest` 声明**（per-monitor v2 + asInvoker）：4K/225% 下截屏尺寸与点击坐标才不会错位；不提权，提权后反而点不到普通权限窗口的按钮。实测冻结版 `GetDpiForWindow=216`、识别与点击坐标与源码一致。
- **`--collect-all rapidocr_onnxruntime` 是必需的**：OCR 的两个 onnx 模型和字库是包内数据文件，漏了就启动即报错。`onnxruntime` 不用 collect-all（PyInstaller 自带 hook 会收齐 capi 动态库）。
- **删了 `cv2\opencv_videoio_ffmpeg*.dll`**：那 28MB 只服务 `cv2.VideoCapture`，本程序只截屏，用不到。
- **`build.bat` 保持纯 ASCII**：这一个字节的代价很大——曾有一行 REM 里混进中文，cmd.exe 按当前代码页逐字节读批处理，多字节串把后续字符吞掉，`setlocal` 报成 `'ocal' is not recognized`，连 `if errorlevel 1 goto :fail` 一起失灵，于是**每次打包都「假装成功」，exe 一直停在旧版本**。改完 build.bat 后看一眼输出，出现 `'ocal'` 之类就说明又进了非 ASCII 字符。
- **`templates\*.png` 会一起复制过去**：模板是 exe 旁边读的，漏复制就等于所有模板目标静默失效（OCR 通道仍在跑，所以现象是「明明有模板却检测不到」）。`xcopy /Y templates\*.png` 只搬 png，探测用的临时目录不会跟过去。
- **首次运行可能被 SmartScreen/杀软拦**：exe 未签名，点「仍要运行」即可；若被杀软误报，把整个目录加入白名单。

想让它随 Windows 登录自动跑起来：打包后把 `LiveAutoClicker.exe` 的快捷方式放进「启动」文件夹（`Win+R` → 输入 `shell:startup` → 回车）。配合默认的 `auto_start`，开机即开始扫描。
